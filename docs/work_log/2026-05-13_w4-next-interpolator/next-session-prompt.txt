### §1.3 세 path 후보 (plan v6 round 에서 evaluate)

Codex 의 planning-phase Q4 trigger 가 본 경우를 plan v6 territory 로
명시. W4-A-sibling 단순 mirror 가 아닌 design 결정 영역.

#### path δ1 — mechanical W4-A-sibling mirror

`collectLayoutXmls` (AarResourceWalker) + `ParsedNsEntry.LayoutXml` +
bundle byType[LAYOUT] entries + per-name path-style placeholder
(`axp/layout/<name>.xml`) + callback ResourceType.LAYOUT routing.
existing pattern 의 가장 작은 delta. 단 W4-A 의 5번째 sibling helper
도입으로 copy-mirror 의 redundancy 가 노출 (LM-W4-NEXT-AAPT-XMLS).

#### path δ2 — data-driven feed registry

4 existing sibling helpers (color / animator / drawable / interpolator)
+ 새 layout helper 를 단일 data-driven registry 로 refactor. higher
initial cost — 향후 AAR resource type (font / raw / transition /
mipmap / xml) 에서 payback. wider regression surface — T17 + T20 +
MaterialFidelity + chip + basic + minimal 모든 step 통과 의무.

가능 shape:

```kotlin
internal enum class AarFeedKind(val dirPrefix: String, val resType: ResourceType, val placeholderPrefix: String) {
    COLOR_STATE_LIST("res/color/", ResourceType.COLOR, "axp/color/"),
    ANIMATOR_XML("res/animator/", ResourceType.ANIMATOR, "axp/animator/"),
    DRAWABLE_XML("res/drawable/", ResourceType.DRAWABLE, "axp/drawable/"),
    INTERPOLATOR_XML("res/interpolator/", ResourceType.INTERPOLATOR, "axp/interpolator/"),
    LAYOUT_XML("res/layout/", ResourceType.LAYOUT, "axp/layout/"),
}
```

NsBucket 의 4 (now 5) Map<String, String> fields 도 단일 Map<Aar
FeedKind, Map<String, String>> 로 통합 가능. callback.getParser
의 when branch 도 data-driven dispatch.

#### path δ3 — selective layout pass

실 IT probe 가 요청한 layout XML 만 enumerate. bundle footprint 작음
— 단 walker 의 runtime feedback loop 가 현재 없음 (현 architecture
는 startup-time bundle build). probe-driven on-demand 가능한지 design
검토 필요.

### §1.4 plan v6 round 에서 추가 evaluate 항목

- W4-B-C drawable placeholder shape (`axp/drawable/<name>.xml`) + W4-
  NEXT interpolator (`axp/interpolator/<name>.xml`) 가 single helper
  `axp/<resource-type>/<name>.xml` 로 일반화 가능한지 (data-driven
  feed registry 와 자연 연계).
- `Resources_Delegate.getLayout(Resources, int)` 의 자체 value-format
  gate 존재 여부 (LM-W4-B-J operationalization for LAYOUT sibling).

  (Resources, int)` 신호 — `getXml` 패턴과 동일 한지 확인.

  parser 를 어떻게 consume 하는지. LayoutInflater 는 DrawableInflater

  / `<view-class>` 등 layout-specific 구문 처리). `SelectorXmlPullParser
  .fromString` 가 호환되는지 verify 의무.
- AAR layout XML 의 `<include>` / `<merge>` 가 recursive layout
  reference 를 트리거할 가능성 — `design_text_input_start_icon` 가
